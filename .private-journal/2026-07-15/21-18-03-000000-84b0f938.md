[BINARY-RE:dynamic] Human-mediated DEK recovery was tested against Granola 7.427.2 without exposing credentials. Apple Keychain Access has wildcard keychain access and the private `com.apple.authorization.extract-password` entitlement, while `/usr/bin/security` does not; a metadata-only `security find-generic-password` query could not see the Granola item. Keychain Access located the item, but copying its password produced an empty clipboard. Static inspection explains this: `keychain.node` stores and returns the DEK as raw 32-byte Foundation `Data`/Node `Buffer`, not UTF-8 text. The matching encrypted-file framing is 12-byte IV + AES-256-GCM ciphertext + 16-byte authentication tag. Two user-approved, network-denied launcher experiments failed before any Keychain call: `ELECTRON_RUN_AS_NODE` was ignored because the `RunAsNode` fuse is disabled, and a `NODE_OPTIONS --require` preload was rejected for the packaged app. Both reached Granola's normal bootstrap and then hit its existing single-instance guard; neither loaded the probe. No DEK was read or created, no token was printed, and no Keychain, encrypted-session, or authentication state was modified. Root cause: owning executable entitlements would authorize the read, but Granola exposes no supported code-execution or human-consent bridge that returns the binary item to Muesli.
